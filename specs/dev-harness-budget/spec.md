## 1. 背景与动机（why）

- 本仓库的功能开发按 spec-driven 工作流分批推进，每批涉及多个阶段、角色、模型与通道（见 [model-routing.md](../../docs/development/model-routing.md)）。目前没有统一方式回答“某一开发批次实际用了多少 token、发了多少次模型请求和工具调用、墙钟耗时多少、重试和返工有多少”，也看不出哪些用量**根本没观测到**。
- 缺少这些事实，后续讨论开发成本、模型路由取舍或节省措施时只能凭印象；而把未观测的用量当成 0、把流式累计快照相加、把并行会话耗时相加，都会得出看似精确但错误的数字。
- 本 feature 先做“**只观测、不约束**”：在开发批次运行**之后**，按需对显式选定的批次生成一份本地用量元数据报告，诚实区分已知、未知与未覆盖。阈值、限额、自动处置等约束性能力留待后续版本，在有真实数据之后再决定。
- **与产品运行时预算无关**：[plan.md §7.2](../../docs/plan.md#72-模型接口对接) 与 [architecture.md §5.5～§5.6](../../docs/architecture.md#55-多-agent-编排d-019) 中的每角色 token 上限、每作业成本上限、常驻作业每日 / 每台预算、`budget_exceeded` 降级，属于产品运行时（D-019 / D-022），不是本 feature 的范围；本 feature 也不是产品作业引擎（§5.4）的一部分。[model-routing.md 规则 8](../../docs/development/model-routing.md#rule-8) 同样区分开发工作流与产品运行时。

## 2. 目标与非目标

### 目标（what）

- 对用户**显式选定**的本仓库开发批次及其已知会话（含已有、已授权的历史记录），在运行结束后**按需**生成本地用量元数据报告。
- 报告的度量：输入 / 输出 / 缓存读 / 缓存写 token（分维度累计）、单请求输入峰值、模型请求尝试次数、工具调用次数、批次观测墙钟窗口与会话耗时合计、传输重试与语义返工次数。
- 报告按批次、会话、阶段、角色、模型、通道、基线提交分组，可附可选的人工标注；缺失维度显示为“未知”。
- 每个数字都带覆盖状态：未知不等于 0，已知小计不冒充完整总计，未去重的汇总不冒充精确总计。
- 报告只含元数据与证据引用，不复制任何原始内容。
- 用至少一个真实开发批次做试点、用合成样例覆盖边界语义，证明可用性。

### 非目标

- **不做任何约束或干预**：不设 token / 时间 / 费用上限，不做调用准入、自动停止、降级、改路由、改思考强度、改重试策略。
- **不做产品运行时功能**：不涉及产品作业、自主度、预算、计费、价格同步、产品 UI；不依赖产品后端 agent / 作业引擎实现。
- **不做费用计算**：v1 不把 token 换算为金额；token 数不是计费金额。
- **不做实时看板或常驻服务**：只做运行后按需报告。
- **不新增强制性开发流程规则**：不修改 AGENTS.md、workflow.md、model-routing.md，不要求开发者在每批次后必须生成报告；v1 本身不改变全局规则。本次起草不新增 ADR，但这只描述本次起草，不是对今后的豁免或禁令：后续若出现实际的架构 / 工作流设计决策，仍按现行 ADR 与审批规则处理。
- **不改变被观测批次**：不改其冻结 AC、checklist、模型路由、审核或 Gate 状态。
- **不为采样额外发起模型调用或重跑业务任务**；不建设完整的全局计费 / 记账服务。
- 不在本 spec 中选择存储格式、传输方式、数据库、CLI / RPC / hook / 框架等技术方案（留待 Gate 1 之后的 Plan）。

## 3. 需求条目

每条需求格式：需求（what）→ 验收规则（AC）。以下验收规则全部未勾选：它们是待实施的需求，不是完成声明。

### 术语与口径

- **选定来源总体**：用户为某批次显式选定的记录集合。所有覆盖、缺失与总计陈述都只相对于这个总体，不代表全局所有实际 API 调用。
- **已知小计 / 完整总计**：已知小计 = 已确认去重总体内、最终值已知的记录之和；只有选定总体内全部记录最终值已知且已确认去重时，才给出完整总计，否则完整总计为未知。
- **未知 / 0 / 部分观测值**：未知不等于 0；占位或默认 0 不是实际 0。来源确实上报的可信、单调的非最终值只作为“部分观测值（下界）”单独保留，不计入已知小计。
- **来源上报输入**：按来源声明语义，把互斥的普通输入、缓存读、缓存写各计一次后的和；它不是账单金额，也不是精确的请求前上下文大小。
- **尝试 / 重试**：尝试 = 实际观测到的一次模型请求尝试；重试 = 有可靠来源关联、明确指出是先前某次尝试的重试。
- **测量完整性 vs 执行结果**：测量完整性（完整 / 部分 / 不可用）描述观测是否齐全；观测到的执行结果（完成 / 失败 / 取消 / 超时 / 未知）描述被观测工作本身。完整测量可以描述一次失败的执行，也不代表任何业务验收。测量完整性按度量分别判定（如时间、用量各自完整 / 部分 / 不可用）；某一度量完整不代表其他度量或整次观测完整，例如耗时已知但用量缺失时，整次观测不得标为完整。
- **批次观测墙钟窗口**：选定会话中最早的确认开始时间到最晚的确认结束时间；只有在这些边界都已确认且彼此可比时才给出，不声称覆盖来源未覆盖的时间。

### R-001 显式选择的输入与运行后按需报告

- **what**：只处理用户为本仓库显式选定的开发批次及其已知会话；在运行结束后按需生成报告，不要求常驻服务。生成报告本身不发起任何模型或网络调用，也不影响被观测的任何开发工作。
- **验收规则**：
  - [ ] AC-001-1 输入范围只来自显式选择：给定一组可读记录，其中只有部分被选入批次，报告只包含被选中的记录；未被选中的会话、其他项目目录和私有文档目录不被读取或出现在报告中（用含“未选中”记录的合成样例验证）。
  - [ ] AC-001-2 已有、已授权的历史记录可作为输入，与新记录使用相同的度量语义；生成报告不需要被观测会话仍在运行，也不需要任何常驻进程。
  - [ ] AC-001-3 生成报告过程中，观测到的模型调用**尝试**与网络请求**尝试**均为 0。验证须同时满足：在无凭证、断网条件下对合成样例成功生成完整报告；并在外部调用边界（模型调用与网络出口）观测到的尝试次数为 0。仅“断网仍成功”不足以证明，因为工具可能发起请求后捕获网络错误。本条不指定观测手段。
  - [ ] AC-001-4 观测失败（来源缺失、不可读、格式不符）时，报告把对应部分标为“不完整”或“不可用”并说明原因，不报告成功、不填 0。生成报告不影响被观测工作，以三项相互独立的观测验证：（a）生成前后被观测源记录与既有产物的哈希不变——它只证明这些文件未被改写；（b）被观测 feature 的业务状态（spec / AC / checklist / Gate 状态记录）生成前后一致；（c）生成过程未发出任何启动、停止、取消、中断或其他控制会话 / agent 的动作。哈希不变本身不证明 agent 未被中断或任务状态未受影响。报告在运行后生成，以上证据可用合成样例或受控边界取得，不需要额外运行付费的真实 agent。

### R-002 分组维度与人工标注

- **what**：每条观测记录归属到批次、会话、阶段、角色、模型、通道、基线提交等维度；维度来自源数据或可选的人工标注。缺失的维度如实显示为未知。
- **验收规则**：
  - [ ] AC-002-1 来源未提供、也无人工标注的维度显示为“未知”，不以默认值、推测值或空字符串冒充；“未知”在分组汇总中作为独立一组出现。
  - [ ] AC-002-2 人工标注（如阶段、角色、返工、可比性说明）可选；报告标明每个维度值来自源数据还是人工标注；添加或修改标注不改动源记录。
  - [ ] AC-002-3 报告可按阶段、角色、模型、通道分组。守恒校验**按每个分组维度分别进行**：在同一维度内（例如只按阶段），各组（含“未知”组）的已知小计之和等于批次已知小计；不同维度的合计（阶段合计 + 角色合计 + 模型合计）绝不相加。该等式只在同一声明度量语义、且已确认去重的同一记录总体内成立；未确认去重的部分不参与该等式，并单独标注。

### R-003 token 度量语义

- **what**：按来源声明的语义区分互斥维度与子集字段，分别给出批次累计与单请求输入峰值；未知与 0 严格区分。
- **验收规则**：
  - [ ] AC-003-1 输入、输出、缓存读、缓存写分维度累计。示例：一个已完成请求的互斥字段为普通输入 100、缓存读 40、缓存写 10、输出 20（其中推理 5，来源声明推理已含在输出内），报告总计为 **170**，不是 175。
  - [ ] AC-003-2 来源声明为子集的字段（如推理之于输出、一小时缓存写之于缓存写）只作为子集展示，不再次计入总计；不同来源的重叠计数器只有在其声明语义能对账时才合并，否则该部分标为“口径未对账”，不给出精确总计。不假设每个来源都提供全部字段，缺失字段显示为未知。
  - [ ] AC-003-3 单请求输入峰值与批次累计分开展示。峰值 = 单个请求“来源上报输入”的最大值（互斥的普通输入、缓存读、缓存写各计一次），标为“来源上报输入峰值”，不称“计费输入”，不称精确的请求前上下文大小，不承诺与实际账单或金额一致。示例：AC-003-1 中的请求输入为 100 + 40 + 10，输入峰值为 **150**，加上输出 20 的 token 总计为 **170**。来源自身给出的估计值、以及报告展示的任何上下文大小估计，都必须标为“估计”。峰值同样标明覆盖范围；不需要读取原始上下文内容。
  - [ ] AC-003-4 只有经确认的实际 0 才显示为 0；来源的占位或默认 0、未上报、待定的用量一律记为未知。非最终用量的最终值为未知；若来源确实上报了可信、单调的部分值，可作为“部分观测值（下界）”单独展示，但不计入已知小计。示例：已知记录合计 50 加 1 条未知记录 → 报告显示“已知小计 50、未知 1 条、完整总计未知”，不显示“总计 50”。

### R-004 累计快照与重复去重

- **what**：流式用量是累计快照，不是增量；同一响应、同一工作在多处出现时只计一次；无法可靠去重时如实标出。
- **验收规则**：
  - [ ] AC-004-1 同一响应的流式用量快照依次为 6、10、最终 12 时，该响应计为 **12**，不是 28。缺少最终权威值的响应标为“非最终”，最终用量未知，不计入已知小计；若其最后的快照来自可信、单调的来源（例如 10），可单独显示为“部分观测值（下界）10”，不当作最终值，也不填 0。
  - [ ] AC-004-2 同一已完成响应在不同事件或摘要中重复出现时只计一次（用同一响应在两处出现的合成样例验证）。
  - [ ] AC-004-3 父会话、子会话、会话汇总之间的重叠用量不重复计入。缺少可靠的重叠关联信息时：各来源各自的已知值照常保留和展示；跨来源去重后的汇总标为“未完全去重”、数值未知；未去重的相加结果不得称为精确的已知小计或完整总计。本条不要求建设全局记账平台。

### R-005 请求、工具、重试与返工计数

- **what**：区分模型请求尝试、（必要时）模型轮次、工具调用、传输重试与语义返工；纳入来源能暴露的重试、压缩、摘要和嵌套模型用量，并说明哪些路径未被观测。
- **验收规则**：
  - [ ] AC-005-1 模型请求尝试数、工具调用数分别计数；工具调用不计为模型调用。来源暴露的嵌套工具调用按其标识纳入并去重；来源未暴露的嵌套路径覆盖状态标为未知。
  - [ ] AC-005-2 一次失败与一次成功的两个事件**不自动**构成重试对。只有当可靠的来源关联明确指出第二次尝试是第一次的重试、且两次尝试均实际观测到时，才计为“尝试 2、重试 1”，不因只剩最终成功结果而计为 1。缺少这种关联时：可观测的尝试照常计数（尝试 2），重试数标为未知，不从先后顺序或成败状态推断。
  - [ ] AC-005-3 来源暴露的重试、压缩、摘要、工具内嵌套模型用量计入并标为“已覆盖”；来源未暴露的路径列为“未观测”，不视为免费或 0。来源不能披露物理请求次数时，报告“观测到的尝试数”及其覆盖说明，不把助手消息数标为“全部物理 API 调用数”。
  - [ ] AC-005-4 语义返工只来自来源的显式标记或人工标注，并与传输重试分开计数；新增范围或更换通道不会被自动记为返工。

### R-006 墙钟耗时与会话耗时

- **what**：区分批次观测墙钟窗口与各会话耗时之和；区分测量完整性与观测到的执行结果；时间不完整时如实报告部分观测值。
- **验收规则**：
  - [ ] AC-006-1 两个会话在 0～10 秒内并行运行、开始与结束均已确认时，批次观测墙钟窗口报告为 **10 秒**；会话耗时合计 **20 秒** 单独列出，可标为“会话耗时合计”，但不得被标为批次墙钟耗时或批次耗时。批次观测墙钟窗口按“术语与口径”定义：边界不齐全或不可比时不给出该窗口（标部分或未知），且不声称覆盖来源未覆盖的时间。本条不指定时钟实现。
  - [ ] AC-006-2 超时本身不等于耗时未知或测量不完整。有可比的开始时间且有确认的结束时间时，报告已知耗时，并标明观测到的执行结果（超时 / 失败 / 取消），不报告为正常成功；例：0 秒开始、30 秒确认超时结束 → 耗时 30 秒已知、时间度量的测量完整、执行结果“超时”；这里的“完整”只指时间维度，用量等其他度量及整次观测的完整性另行独立判定，耗时已知而用量缺失时不得报告为整体完整。缺少确认结束时间时，测量标为“部分”或“不可用”，报告已观测部分耗时（如有）或未知，不报告为 0、也不报告为完整耗时。时间戳不足时不声称推导出了关键路径或因果顺序。

### R-007 报告内容、隐私与可比性

- **what**：默认给出简洁摘要并可按需展开明细；报告只含声明过的统计元数据、派生聚合与证据引用，绝不复制原始负载；如实披露比较条件，明确标出条件不同或未知的批次。
- **验收规则**：
  - [ ] AC-007-1 默认摘要包含：已知小计（以及能给出时的完整总计）、按阶段 / 角色 / 模型 / 通道的分组；每项度量在声明的选定来源总体内的已覆盖 / 未覆盖 / 缺失计数，并明确标出计数单位（会话 / 请求 / 来源记录，按适用者）及该度量所依据的总体（分母）；不同分组层级的计数不混合相加或相比——百分比只在分母已知时给出，否则标为未知，且不把“选定记录已覆盖”表述为“全部实际 API 调用已覆盖”；分开展示的测量完整性（完整 / 部分 / 不可用）与观测到的执行结果（完成 / 失败 / 取消 / 超时 / 未知），完整测量不代表业务验收；证据引用（来源标识、来源版本、基线提交、比较条件）。明细按需展开，默认不做事件全量回放；不要求对全局实际调用做实时普查。
  - [ ] AC-007-2 报告、日志与提交到仓库的任何文件均不包含原始业务 / 文本负载：提示文本、思考内容、工具参数、工具结果正文、凭证、私有路径。只允许出现声明过的统计元数据（如工具结果附带的用量计数）、派生聚合与不敏感的证据标识；不得把整条原始记录重新序列化输出。验证：只在合成样例的禁止负载字段中放入哨兵字符串（不放入合法用量字段），生成报告后在所有输出与日志中检索不到哨兵，同时合法的用量元数据仍被正确统计。
  - [ ] AC-007-3 真实观测数据与报告只写入用户本地、不被 Git 跟踪的位置；仓库中只出现合成样例证据，输入事件日志与私有数据不进入 Git。验证：在干净的测试沙箱中生成报告前后，`git status` 显示的仓库状态不变——既无被修改的已跟踪文件，也无新的未忽略文件；运行时观测不提交。
  - [ ] AC-007-4 比较条件作为元数据披露。基线提交不同只是披露项，本身不构成“不可比”；模型 / 配置、任务范围或度量语义发生变化时标注“条件不同、不可直接比较”；可附可选的人工可比性说明（标明来源与出处），但不移除变化警示；比较条件缺失时可比性标为未知。报告不基于单个样本自动给出 token 节省或质量结论；不出现金额字段，token 数不被表述为计费金额。

### R-008 试点与验收覆盖

- **what**：用至少一个真实开发批次证明可用，用合成样例覆盖边界语义；试点不影响被观测 feature 的任何既有约束。
- **验收规则**：
  - [ ] AC-008-1 至少对一个经用户显式授权的真实开发批次（可以是已有、带可用用量的真实历史批次）生成报告，过程中不新增模型调用、不为测量重跑已完成任务；试点记录写明它只证明可用性，不是统计上充分的基线，也不证明节省。
  - [ ] AC-008-2 合成样例至少覆盖三类情形：已知完整；重复累计快照加重试；未知或中断加并行。可以用最少的样例组合覆盖多个类别；合成样例不含任何真实负载内容。
  - [ ] AC-008-3 试点不改变被观测 feature 的冻结 AC、checklist、模型路由、审核与 Gate 状态；试点记录不构成该 feature 的验收；试点批次的选择不以 desktop-shell 或 workbench-interaction 完成为前提。

## 4. 约束与依赖

- **工作流**：本 feature 自身遵守 [workflow.md](../../docs/development/workflow.md) 与 [model-routing.md](../../docs/development/model-routing.md)；Gate 1 批准前不进入 Plan。根 `AGENTS.md` §5 七条工程准则、隐私规则（用户文档、私有数据、凭证永不入库；`.gitignore` 锚点不得移除）、审核员 A 只读审查固定提交等现行规则不变，本 feature 不修改它们。
- **不依赖其他 feature 完成**：不依赖产品后端 agent / 作业引擎（[architecture.md §5.4～§5.6](../../docs/architecture.md#54-作业引擎边界)），不依赖 desktop-shell、workbench-interaction、frontend-workbench 等任何在研 feature 完成；可在 Plan 中使用开发环境已有的 pi 元数据作为来源。
- **与产品预算的边界**：产品运行时的模型三档、每角色 / 每作业 / 常驻作业预算（[plan.md §7.2](../../docs/plan.md#72-模型接口对接)，D-019 / D-022 / D-023）不受本 feature 影响，本 feature 也不为其提供实现。
- **来源语义参考（pi 1.4.0 安装包文档，非本仓库文件，不锁定实现方式）**：
  - `docs/json.md`：`message_update` 携带的 `usage` 是该助手响应最新的**累计**用量，供应商流式期间不上报时可一直为 0 直到完成；`message_end` 是权威的最终消息；`compaction_end` 成功时可含用量；工具执行事件以 `toolCallId` 关联生命周期，结束事件含 `durationMs`；`agent_end` 只表示一次底层运行结束，之后仍可能自动重试或压缩，`agent_settled` 才表示该会话级运行不再自动继续。
  - `docs/message-types.md`：`reasoning` 已含在 `output` 中，不得重复相加；`cacheWrite1h` 是 `cacheWrite` 的子集；工具结果的可选 `usage` 表示工具内嵌套模型工作，计入整会话统计但不属于主模型调用用量；原始私有内容与用量处于同一记录中，因此摘要不得复制负载内容。
  - 上述语义用于约束 AC 的正确性；具体读取方式、可覆盖范围与限制在 Gate 1 之后的 Plan 中确定，本 spec 不承诺完整覆盖。
- **存储**：真实观测只放用户本地、不被 Git 跟踪的位置；如需调整忽略规则，由 Plan 提出并经批准，本次不修改 `.gitignore`。
