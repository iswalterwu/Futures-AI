## 审核发现（R1）

### P2-1 按度量的完整性未定义，“整体观测完整 / 退出码 0”对任何受支持的原生输入都不可达

- **位置**：plan.md L69（退出码定义）、L114（传输重试一行）、§3.3 完成度规则（`error` = interrupted）、§4.3 第 4 条、L178（§4.4）、L182（§4.5 中的“整体完整 =”）；§5 中 F1 与 AC-001-3 的映射。
- **具体失效**：§4.5 要求 tokens / attempts / tool_calls / retries / rework / timing 全部 complete 才算整体完整，但其中 attempts、tool_calls 等的 complete 判据**没有定义**。retries 的规则使整体完整无法达成：
  - session-v3 的重试**永远是未知**（L114）；
  - json-events 只有在存在重试括号时重试数才算已知（L178，“无标记即 unknown”），而重试括号必然包含一条 `stopReason=error` 的 assistant 记录；按 §3.3 这条记录属于 interrupted，永远不是 final-known，于是 §4.3 第 4 条不成立，tokens 必然不完整。
  - 结论：退出码 0 / `observation=complete` 是不可达状态，F1“已知完整”的期望退出码与 observation 字段无从确定；AC-001-3 的测试实际依赖“报告产物写出”这一解读，但 Plan 没有写明。
- **修复（Plan 层）**：
  1. 逐项定义各度量的 complete / partial / unavailable 判据及其适用范围；
  2. 要么调整规则使整体完整在一致的口径下可达，要么明确声明原生适配器下不可达，并据此重新定义退出码；
  3. 写明 AC-008-2 中的“已知完整”是按度量判定（例如 token 完整总计已知），F1 断言的是对应度量，而不是整体完整；
  4. 写明 AC-001-3 中“完整报告 = 报告产物完整写出”的解读；有异议则回 Clarify；
  5. 如需测试“全部已知”时的聚合逻辑，可以在已声明的系统边界 `build_report(manifest, facts, …)` 注入类型化的合成 `SourceFacts`，标为合成数据，不复写算法；不得声称原生文件适配器提供了它实际无法提供的事实。

### P2-2 重试计数的范围超出可观测范围，判定规则不对称

- **位置**：plan.md L112、L114、L178、§3.6 `retries`。
- **具体失效**：只要重试括号闭合，就报告“传输重试总数 known”。但单次尝试内部的 provider / SDK / HTTP 层重试本来就不可得（L112），称“总数”超出了实际观测范围。同时，一个已 settled、没有任何重试标记的流在同一证据层级上被判为未知，而有括号的流被判为已知总数，规则不对称；还会诱导夹具为了“已知”而人为制造失败。
- **修复**：把该度量命名为“观测到的 pi 自动重试（assistant 级）”，在这个范围内一致地定义已知 / 未知（例如已 settled 且无标记时，判已知 0 或一律未知，二选一并写明理由）；把 provider / SDK / HTTP 层重试列入 `unobserved_paths`；摘要重试单列。

### P2-3 “模型请求尝试数”漏掉非 assistant 的模型工作，且没有披露

- **位置**：plan.md L113、L128（§3.3 单位与分母）、§3.6 `attempts` / `unobserved_paths`、L210（AC-005-3 映射）。
- **具体失效**：尝试数只统计 assistant 条目或 `message_end`。以下模型工作既不计入尝试，也没有列入 `unobserved_paths`：
  - compaction / branch_summary 的摘要生成；
  - `usage` 条目（例如 `cache_warm`）；
  - toolResult 中的嵌套模型调用；
  - json 流中失败的 compaction。
  另外，json-events 可能根本不包含 `usage` 条目，但能力矩阵没有把它标为未观测，json 来源的 token“完整总计”可能静默漏掉这部分。结果是 spec AC-005-1 / AC-005-3 要求的覆盖说明不完整，报告看起来像是全部模型请求。
- **修复**：尝试按类别报告并标明范围（主 assistant 尝试、摘要 / usage 记录、嵌套用量记录，后者请求数未知）；在 `unobserved_paths` 中列出不计入尝试的类别，以及 json-events 中不出现的 usage 条目类别；不把 assistant 条目数表述为不带限定语的模型请求尝试总数。

### P2-4 `nested_of` / `duplicate_of` 关系图校验不完整：成环、链式嵌套、多子来源、工具重复计数

- **位置**：plan.md L89-90、L133、L136-141（§3.4 第 5 层）、L208（AC-005-1 映射）。
- **具体失效**：
  - `duplicate_of` 成环会被拒绝，但 `nested_of` 成环（A→B(T1)、B→A(T2)）没有校验。若 (a)～(c) 成立，而 (d) 因子来源维度未知被跳过（或数值恰好相等），两个来源的 token 都会被排除在聚合之外，又不触发任何“未确认去重”分区，§4.3 的完整条件仍可能通过，于是出现假的完整总计并丢失用量（违反 AC-004-3 / AC-003-4）。
  - 链式嵌套（孙 → 子 → 父）未定义：子来源被排除时，它自己的 toolResult 用量是否保留不清楚。
  - `duplicate_of` 与 `nested_of` 混用（同一来源，或交叉成环）未定义。
  - 多个子来源指向同一 (P,T) 的处理未定义。
  - (d) 中“各维之和”的含义有歧义：是逐维相等，还是四维合计相等？
  - 被覆盖的子来源工具计数“照计”，而父来源 `nestedCalls` 也“按 id 计入”，两边的 id 不保证相同，可能把同一次工具调用计两次（AC-005-1）。
- **修复**：在 `load_manifest` 入口拒绝 `nested_of` / `duplicate_of` 联合图中的任何环；明确链式嵌套的语义（或一律进入未确认分区）；多个子来源指向同一 T 时进入未确认分区，除非合计校验一致；把 (d) 写成逐维比较；定义父 `nestedCalls` 与被覆盖子来源工具结果之间不重复求和的规则；为上述每种情况补夹具负例。

### P3（可接受为后续任务，不阻塞）

- **P3-1**（L226 §6）：session-v3 是文件快照，正在进行中的请求不会持久化，也无法证明运行已结束。这一点只写在风险节，没有进入报告文案。建议在摘要的覆盖说明中写明“总体 = 该 `content_sha256` 版本文件中的记录，不证明运行已结束”。
- **P3-2**（§4.5 L182）：明确写出：来源文件不可用或部分可用时，其 `timing` 标注仍计入会话时长与批次窗口，不能因为文件不可用就丢掉它的时间（F6 加 timing 夹具）。
- **P3-3**（L133）：`duplicate_of` 只校验目标为 `loaded`，隐含了“本来源完全包含于 X”的人工断言。建议在报告中把它标为 annotation 断言，由断言者负责，并写明若本来源比 X 多出记录，这部分会被丢弃。
