# Futures-AI 交互架构（interaction.md）

> 人与 agent 如何在同一工作台上协作：双循环模型、作业与四阶段契约、介入机制、交付物与验证性需求、知识回流规则、学习循环与分析协议。

## 1. 定位与设计命题

### 1.1 从"AI 分析软件"到"Agent+人 双循环工作台"

旧定位隐含两个假设：主导对象是"日报/图表"，循环是单向的（数据 → 分析 → 交付即结束）。后果是人的介入无处安放、交付物不是下一轮研究的起点、人的修改无法沉淀。

新定位：**以"作业"为单位的人机共同交付 + 交付物反哺问题 + 与交付共享底座的认知学习。**

- 人的角色是**补充者与共同作者**，不是审批者：人提供意图、来源语境、业务口径、分析框架与判断标准、取舍与定稿决策（§3.1）。
- 对话不是产品主体，只是众多接口之一；主体是作业与产物（§2.4、`designUI.md` §3）。

### 1.2 三类市场产品的错配

| 类型 | 代表形态 | 缺什么 |
|---|---|---|
| 对话优先型 | 通用助手、Perplexity 类 | 产物是附件；数据阶段、改稿阶段没有结构化介入面 |
| 副驾型 | Office / 编程 Copilot | 人只提要求与验收；编辑轨迹不沉淀为可复用规则 |
| 检索终端型 | AlphaSense、行情终端 | 有数据与检索，没有"交付—反馈—再采集"闭环，也没有学习线 |

共同缺失三件事：**人的介入不是一等数据、交付物不是下一轮问题的生成器、知识回流没有闸门**。

### 1.3 第一性原理

1. **人是补充，不是审批**：只有人能提供意图、来源语境、业务口径、分析框架与判断标准、最终取舍；这些是 agent 无法从数据中推导的输入。
2. **介入是一等数据**：每次介入都是可回链的结构化事件，既是协作输入，也是学习原料（§3.4、§6）。
3. **交付物是下一轮问题的生成器**：交付完成即抽取"验证性需求"与 calls，用户确认后生成新作业（§3.6、§9）。
4. **知识回流必须有闸门**：溯源、去重、派生隔离缺一不可，否则自迭代会退化为自引用污染（§5）。
5. **学习与交付共享底座但形态不同**：学习由用户发起（复盘可由 agent 排程）、信息密集、无固定交付模板，以"认知增量"衡量（§4）。
6. **结果是一等数据，但人的权限优先**（D-020）：市场结果校准 agent 的结论、来源的可靠性与（仅供自查的）人的判断；人常掌握非公开信息，agent 不以校准覆盖人的判断，只以镜子呈现（§9）。
7. **agent 有常驻职责与分级自主度**（D-022）：研究台在作业之外按触发器值班（议程 / 收件箱），自主度由用户按档开启，闸门与审批点不随档位放松（§11）。

## 2. 概念模型

### 2.1 核心对象

| 对象 | 定义 | 边界 |
|---|---|---|
| **作业 Work** | 一次交付任务的容器：日报、专题、临时问题、验证追踪；**常驻作业**是带触发器的作业子类（§11） | 有阶段、版本、参与者（人/agent）与状态机（§3.7）；可有子作业（§12） |
| **产物 Artifact** | 阶段产出：数据集与加工配方、分析稿、交付文档、学习笔记 | 版本化；人改与 agent 改都生成新 revision |
| **介入 Intervention** | 人在任意阶段的结构化动作 | 事件化、可回链；不是覆盖写（§3.3–3.4） |
| **知识底座 Knowledge** | 源材料 / 断言 / 派生视图 + 谱系 | 分可信区与派生区；写入必须过闸门（§5） |
| **世界模型 WorldModel** | 品种包 schema 定义的市场状态槽位集合，是断言台账 + 观测之上的视图（D-021） | 槽位带置信 / 时间 / 陈旧 / 状态；人填 agent 不覆盖；一致性是闸门（§10） |
| **分析协议（playbook）** | 从介入、历史产出、访谈与复盘中学到的框架、判断标准、表达与数据偏好 | 显式、可编辑、可版本回退（§6） |
| **Call / 决策 Decision** | 可裁决的陈述 / 用户的取舍（D-020） | 到期自动裁决；校准按作者分桶；用户优先（§9） |
| **主体 Persona** | 角色实例化时的视角参数：关注点 / 框架 + 模型绑定（D-023） | 多主体并行 / 辩论；产物带主体来源徽（§12） |

### 2.2 两条循环与共享底座

```
                ┌──────────────── 共享底座 ─────────────────┐
                │ 数据/知识库（带谱系）+ 世界模型 + 分析协议    │
                └───────┬───────────────▲───────────────────┘
                        │               │
        ┌───────────────┘               └────────────────┐
        ▼                                                │
  ① 交付循环（agent 主跑，人补充）                    ② 学习循环（用户发起或 agent 排程）
  提取 → 处理 → 分析 → 交付物 → calls                  阅读 / 复盘 / 深挖 / 自测
    ▲                    │                                    │
    └── 验证性需求 ←──── 交付物 ─────── 复盘、延展阅读 ─────────┘
        （agent 提取 + 人确认）        （交付物同时是学习材料）
                        ▲
  ③ 常驻研究台（触发器驱动，§11）──▶ 议程 / 收件箱 / surprise / 依据已变 / call 裁决 → 复盘排程
```

- **交付循环**由 agent 主跑、人补充，四阶段见 §3.2；每次交付的产物进入共享底座；定稿时抽取验证性需求与 calls（§9）。
- **学习循环**由用户发起（§4），复盘也可由 call 裁决触发 agent 排程（§9）；产物（笔记/框架/问题）回流底座与协议。
- **常驻研究台**（§11）在两循环之外按触发器运行：向交付循环投喂 surprise、"依据已变"与到期 call，向学习循环投喂复盘；世界模型（§10）是共享底座中的结构化核心。
- 两个方向的互相喂养：交付物是学习材料；学习产物与验证性需求又回流为断言、协议候选或新作业。

### 2.3 四层自迭代

| 层 | 机制 | 回答的问题 | 验收指标 |
|---|---|---|---|
| L1 产物迭代 | 版本、diff、局部重跑 | 这一次能否改到满意 | 人改率、返工轮次 |
| L2 协议迭代 | 介入痕迹 → 分析协议 | 下一次能否更接近人的判断 | 一次通过率、追问密度 |
| L3 知识迭代 | 写入闸门 + 断言台账 + 验证性需求 | 底座是否越来越厚、问题越来越准 | 断言溯源覆盖率、冲突解决时长 |
| L4 校准迭代（D-020） | calls 裁决 + 三方校准 + 决策日志 + 自动复盘 | 判断是否越来越准 | 校准分、surprise 捕获率（§6.4 结果指标） |

L1–L3 以用户满意度为锚，L4 以市场结果为锚；两者的关系是**护栏与目标**：L4 驱动的变更不得使 L1–L3 指标显著恶化（§9）。

### 2.4 主导对象与边界

- **作业**是交付侧的主导对象；**模块工作台**（`designUI.md` §3）是常驻监测面（行情、指标、日历），**常驻作业**（§11）是触发器驱动的值班者，三者不互相替代：模块负责"看"，作业负责"做"，常驻作业负责"值班"。
- **晨间议程**是常驻作业的主产物；**日报**降为导出模板（仍以提供信息为主，由议程与定时作业交付物生成；D-022）。议程不定稿、不回流、过期归档；日报导出的底稿是定时作业交付物，适用定稿语义（§3.5）。
- **对话**保留（时间线、后台运行、角标等能力仍是资产），定位为"自由指令与解释"的接口；结构化介入优先走阶段界面。

## 3. 交付循环

### 3.1 人的五类补充输入

| 只有人能提供 | 对应阶段 | 落成什么 |
|---|---|---|
| 意图与优先级（为什么做、关注什么） | 作业创建 | 作业 / 研究议程 |
| 来源语境（这份材料可信吗、用来干什么） | 数据提取 | 来源说明 + 可信度标签 |
| 业务口径与常识（计算规则、口径选择） | 数据处理 | 加工配方参数 |
| 分析框架与判断标准（怎么看、什么算证据） | 分析 / 交付 | 介入事件 → 分析协议 |
| 取舍与责任（定不定稿、怎么改、改到什么程度） | 交付物 | 定稿决策 |

### 3.2 阶段契约

| 阶段 | Agent 自动做 | 人的介入（动词） | 界面 | 检查点 |
|---|---|---|---|---|
| **提取数据** | 适配器取数、文档解析、网页剪藏（抓取 → 正文 → 模型清理 → frontmatter `.md`，D-018 §3）、粘贴抽取、表格识别、标准化（时序 / 表 / 断言） | 投放文件/链接/粘贴文本；写来源说明（用途·可靠性·时效·口径）；修正抽取映射；标"存疑/仅供假设"；拒绝来源 | 采集台（全局 + 作业内） | 溯源完整性 + 去重闸门；未过闸入"待补证区" |
| **数据处理** | 清洗、单位/时区/日历对齐、重采样、派生指标、对账、表卡 | 指定口径与加工规则、否决错误合并、换源 / 修正别名 / 手工修正值（映射到 data-layer 既有机制，`architecture.md` §3.6）、补计算逻辑/Excel 稿、标注修订 | 处理台（配方 DAG + 对账 diff） | 配方可解释；每个派生值可回溯到源观测 |
| **分析延申** | 按分析协议 + 数据生成结论、证据链、图表，主动提反证 | 注入框架/观点、追问"依据/如果…"、删减、要求深挖、否决结论 | 分析台（结论卡 + 证据链 + 批注/追问） | 每条结论必须有证据锚；无锚标"推断" |
| **交付物** | 组装块式文档/图表/引用、复核（证据可达 / 数字一致 / 来源徽齐全）、生成定稿快照、导出 | 行内编辑、块级批注、指挥 agent 改稿、定稿 | 交付台（块编辑器 + 版本 + diff） | 定稿快照；定稿后自动抽取验证性需求 |

补充规则：

- 各阶段节点由不同**角色**执行（剪藏员 / 对账员 / 分析员 / 撰稿员 / 复核员等），由作业引擎按固定 DAG 调用；角色、模型档与权限见 `architecture.md` §5.5（D-019）。交付前必经复核员。
- 每个阶段以**产物**交接，不以对话交接；交接即生成 revision 与检查点。
- "自动"不意味着不可介入：人的任何介入都合法，只是不阻塞 agent（§3.3）。
- 阶段可因数据不足/冲突停在"待人工确认"；下游仍可用**暂定**产物继续推进，不必等待。
- **扩展（D-020 / D-021 / D-023）**：处理阶段的对账包含世界模型槽位投影与一致性检查（§10）；分析阶段可按主体配置运行多主体辩论并产出 crux（§12）；交付阶段定稿时抽取 calls（§9）；观点 / call / 决策块见 `designUI.md` §5.2。阶段契约本身不变。

### 3.3 介入而不干扰（R1–R6）

1. **一切产物版本化**：编辑不覆盖，产生 revision（base + diff + 作者 + 谱系），可回看、可回滚。
2. **人的介入走旁路**：agent 不被打断，继续在最新已合并快照上工作；人的改稿进入 overlay 层，检查点合并。
3. **下游用最新版本继续**：冲突**不阻塞**流程，只在定稿检查点要求处理；任何时刻可显式"重跑本阶段及下游"，不重跑上游。
4. **无模态确认**：只有破坏性动作（删源、定稿、外发、清库）要确认；其余不弹窗、不审批。
5. **状态与来源可见**：每个块/数字/结论带**来源徽**（外部源 / 人 / agent / 混合）与**状态徽**（草稿 / 暂定 / 已确认 / 冲突），不让人猜哪部分是 AI 写的。
6. **通知节制**：用角标和收件箱，不弹窗打断。

实现含义：上述六条要求作业引擎（`architecture.md` §5.4）提供"阶段状态机 + 产物版本 + 检查点合并 + 介入事件"四项能力；不得用"等待用户确认才继续"的实现替代旁路。

### 3.4 介入事件

```
intervention { id, work_id, stage, artifact_id, base_rev, kind,
               payload(diff / note / framework), reason, basis, outcome, created_at }
```

`basis ∈ {public, private}`：标 `private` 的介入 / 判断不要求溯源到知识库、不触发"来源呢"类质询、不计入来源校准（D-020，§9）；默认 `public`。

字段为示意，最终 schema 以 workflow feature spec 为准。`kind` 不是 UI 埋点，而是**学习分流器**：

| kind | 例子 | 去向 |
|---|---|---|
| `ingest` | 投放材料、写来源说明 | 知识底座（过闸门） |
| `map_fix` / `recipe` | 修正列映射、指定口径 | 数据处理配方 |
| `framework` / `ask_why` | 注入分析框架、追问依据 | 分析协议候选（§6） |
| `delete` / `rewrite` / `veto` | 删减、重写、否决结论 | 分析协议候选 + 产物修订 |
| `source_pref` / `value_fix` | 换源 / 禁源 / 调优先级、手工修正值（处理台，D-018 §4） | data-layer 既有事务接口 + 来源偏好 |
| `approve` / `pin_rule` | 定稿、显式"记住这条" | 定稿快照 / 协议强规则 |
| `slot_fix` | 人填 / 改世界模型槽位（D-021） | 槽位新版本（作者 = 人，agent 不覆盖）+ 断言修订（过闸门） |
| `decision` | 登记 / 修改决策日志、改 call 置信或裁决标准、推翻裁决（D-020） | 决策日志 / calls（§9） |
| `interview` | 首启或重做的结构化访谈回答（D-024） | 画像 / 关注点 / 协议候选（§6.6） |

### 3.5 交付物：块模型、版本与定稿

- **块模型**：权威定义在 `designUI.md` §5.2（块类型、状态、锚）。
- **版本**：编辑产生 revision（base + diff + 作者 + 谱系）；定稿 = 不可变快照。
- **定稿（D-018 §1）**：用户对某个交付物版本的一次**显式**接受动作，交付物状态 `draft → final`；它是"我审过了，这就是我的产出"的唯一明确信号。**不自动定稿**：定时作业长期未定稿 → N 天后标"未审阅"归档（不晋升、不回流）。
  - **效果（按序）**：① 冻结版本 N（块 + 引用的断言版本 + chart-spec + 数据 asof），再改 = 新草稿 N+1；② 升级：留在 N 中的派生断言 → 人工确认（`confirmed_by: deliverable@N`，即 §5.4 晋升门的"人工确认"），本会话被删的 → `rejected_by_user`，被改的 → 新 revision supersedes、来源 = 人；③ 回流：确认内容经写入闸门（§5）入知识底座；④ 派生：抽取验证性需求与 calls → 验证队列（§3.6、§9，非阻塞；call 登记不需用户确认）；⑤ 蒸馏：本会话介入事件 → 分析协议候选（§6.2）；⑥ 导出（可选）。
  - **不是什么**：不阻塞（今天的作业不等昨天定稿；未定稿草稿永远是草稿，其断言留在派生区）；不可撤销（要改就出 N+1 再定稿，N 标 superseded；N 有而 N+1 无的断言在 N+1 定稿时记 rejected）；不是块级（块级动作随时记介入事件，定稿只是把它们结算为接受 / 拒绝）。
  - **显式介入 vs 隐式接受**：改 / 删 / 追问 / 深挖无论定稿与否都是学习信号；"留着没改 = 认可"**只在定稿时成立**。
  - 定稿属破坏性动作（R4 二次确认）；导出 / 外发是独立动作；效果 ③④⑤ 随闸门 L3、验证队列、蒸馏 feature 逐步生效，v1 只做 ① + 派生标记。
- **溯源**：每个数字/结论可追到断言或观测（`architecture.md` §6）；来源徽常驻。
- **改稿**：人可对块批注、直接编辑或下指令；agent 改稿产出新 revision 并给出 diff，人可接受/回退。
- **观点 / call / 决策块**（D-020）：块模型新增三类块（`designUI.md` §5.2）；call 与决策的生命周期见 §9。世界模型槽位被块引用时，定稿冻结所引用槽位的版本（§10）。
- **依据已变**（D-022）：定稿后底层数据 / 槽位变化，一致性台给受影响的块打"依据已变"标记并进议程；不自动改定稿版本，增量版本按 §3.6 生成。

### 3.6 验证性需求 → 新循环

定稿后由 agent 抽取四类需求（第五类 call 见 §9）：

| 类型 | 含义 | 采集计划例 |
|---|---|---|
| 延展采集 | 补更长历史、更多地区/品种/维度 | 主动：一次性深挖并入库 |
| 证据追踪 | 跟踪某数据/公告/报告的后续变化 | 定时：按发布节奏周期采集 |
| 假设验证 | 给"若…则…"的观察条件与触发阈值 | 事件：触发条件满足时采集/提醒 |
| 反证搜索 | 主动找与结论相反的证据 | 主动 + 定时 |

每张验证卡带：问题、为什么现在问（回链交付物块）、期望来源、时效/节奏、优先级。**用户确认闸门**：接受 → 生成新作业（继承父作业与已有产物）→ 回到提取阶段；拒绝/稍后 → 留在验证队列。

需求的新来源（不改四类）：世界模型的恒等式残差与基本面 vs 市场隐含分歧（§10）；多主体辩论的 **crux**（若知道即可裁决的事实，§12）；crux 可直接登记为 call。采集计划新增"裁决取证"（call 到期自动取数，§9）；A2 档下证据追踪 / 裁决取证类子作业可由常驻作业自动创建（§11），生成新的分析作业仍要用户确认。

监测到变化 → 通知 + 生成**增量版本**（不整篇重写）。验证队列与"数据发布日历"模块天然衔接；数据台的预期表与 surprise（§11）是增量版本的主要触发源。

### 3.7 作业与产物状态

- 作业状态：`draft → collecting → processing → analyzing → delivering → delivered`，可进入 `verifying`；旁路状态 `paused / needs_human / blocked / failed / cancelled`。
- 产物状态：`draft / provisional / confirmed / conflict`（界面语义：`designUI.md` §2.4）；交付物另有定稿状态 `draft / final`（§3.5）。
- "待人工确认"不阻塞后续阶段（R3）；状态枚举以 workflow feature spec 为准。
- 常驻作业状态（示意）：`armed → triggered → running → delivered / skipped`，超预算进 `budget_exceeded`（降级为提案，§11）；call 状态：`open → due → hit / miss / unresolved`（§9）。

## 4. 学习循环

### 4.1 定位与触发

**格物致知**（学习循环的产品区，D-018 §5；二级导航：阅读 · 复盘 · 深挖 · 笔记）是**用户发起**的第二工作区，服务于缺少新数据/新观点时的复盘与认知强化。触发方式：

- 用户主动进入格物致知、选择主题或材料；
- agent 在作业收尾/焦点带提议"是否复盘/深入"；
- 知识缺口图驱动的延展阅读建议（§4.3）；
- **agent 排程**（D-020 / D-022）：call 裁决后教练台自动生成复盘草稿进"复盘"与收件箱；用户可忽略，不弹窗。这是学习循环唯一的 agent 发起通道，节奏仍由人掌握。

### 4.2 学习会话结构

1. **主题与目标**：用户选题，或从交付物"深入此主题"。
2. **材料**：知识库检索 + 延展阅读建议（标注来源与可信度；外网检索按隐私开关）。
3. **陪读**：解释、术语、机制、类比、反例。
4. **自测/复盘**：主动回忆、错题、可选间隔重复。
5. **发散**：多角度、跨品种、历史对照。
6. **产物**：笔记、概念图/大纲、学习日志、待验证问题、认知缺口清单。

### 4.3 学习产物与回流

- 笔记/框架 → 派生区（`origin=derived` + 学习会话谱系，§5）。
- 新问题 → 验证队列（§3.6）。
- 框架候选 → 分析协议（§6）。
- 认知缺口 → 延展阅读与采集建议。
- 复盘结论 → 协议候选（`source=postmortem`）+ 来源校准更新 + 决策日志的复盘链接（§9）。

### 4.4 与交付循环的差异

| 维度 | 交付循环 | 学习循环 |
|---|---|---|
| 主导 | agent 主跑，人补充 | 人主导节奏（复盘可由 agent 排程），agent 陪读/出题/串联 |
| 产物 | 交付物（可定稿） | 认知产物（笔记/概念图/问题） |
| 信息密度 | 结论优先、证据收敛 | 信息密集、多源并置、引用优先 |
| 质量判据 | 一次通过率、人改率 | 缺口闭合、认知产物被后续作业引用 |

### 4.5 界面原则

阅读器优先、双栏并置、引用常驻；无固定交付模板；视觉令牌与工作区一致但布局更"文档优先"（`designUI.md` §3.7）。

## 5. 知识回流与自迭代（D-017）

### 5.1 三类内容、三种入口

| 内容 | 例子 | 处理 |
|---|---|---|
| **源材料** | 用户投放的 PDF、网页、公告，外部抓取的数据 | 原件不可变；只做指纹去重防重复解析；保留完整谱系 |
| **断言** | "某地库存 10 月 27 日为 X 吨" | 进入**断言台账**（去重单位）；可被人/agent 生产，须回链来源 |
| **派生内容** | 分析结论、观点、笔记、图表摘要、**用户历史分析**（冷启动摄取，作者 = 人，`source_kind=user_history`，D-024） | 进入**派生区**（`origin=derived`），带推导 DAG；不进入"独立证据"计数 |

"派生区"是逻辑分区（`origin=derived`），不要求独立物理目录；文本落点见 `architecture.md` §4.4。

### 5.2 写入闸门 L0–L5

| 层 | 做什么 | 命中/失败后 |
|---|---|---|
| **L0 溯源闸门** | 每条内容回答：来源、定位（页/块/行）、时间（发布/抓取）、作者类型（外部/人/agent） | 缺项 → 隔离区，不参与自动分析引用 |
| **L1 原文指纹** | 原始字节 sha256 + 规范化文本 sha256 | 重复上传只更新 `last_seen` |
| **L2 块级近重** | SimHash/MinHash + bge-m3 余弦；同文多来源 → 互证计数 | 近重不新增块，挂到已有块 `sources[]` |
| **L3 断言归并** | 抽取 {主谓宾/值, 期, 地区, 单位, 口径, 极性} → 归一化 → canonical key 精确匹配 + embedding 候选 + 判定 | 同断言同值 → 加证；同槽位异值 → claim revision + 冲突；新断言 → 插入 |
| **L3.5 模型一致性门**（D-021） | 断言落入世界模型槽位时检查品种包恒等式（含允差）与同槽位冲突 | 违反**不拒绝** → 标冲突 + 进冲突队列 + 产生验证性需求（§10）；人填槽位不被 agent 覆盖 |
| **L4 派生隔离** | 派生内容带 DAG、`origin` 标记；不进入独立证据计数 | 只能作为"我们的分析"被引用；晋升需人工确认或独立外部源互证 |
| **L5 检索期去重** | 检索末端执行（MMR/断言聚类 + 派生降权） | 规则与展示见 §5.6 |

### 5.3 六种判定（"库里已有的不放"的可执行版本）

| 情况 | 是否新增 | 处理 |
|---|---|---|
| 同一文档重复上传 | 否 | 更新 `last_seen` |
| 同一事实、不同来源 | **不新增断言** | 给已有断言加**证据边**（互证 +1）——简单"不放"会丢掉最有价值的多源互证信号 |
| 同一事实、不同数值 | 不覆盖 | 新增 claim revision + 冲突标记（期货数据修订是常态） |
| 同一结论、不同证据/推理 | 是（新派生） | 独立派生保留，建 derived-from 边；证据源相同则降权 |
| 相同内容的派生重复 | 否 | 证据集合指纹 + 结论签名相同 → 复用旧派生、更新时间 |
| 无溯源/噪声 | 不进可信区 | 隔离区，可人工补证后再入 |

**去重语义 = 归并 + 加边**，不是丢弃。工程约束：幂等（同样内容重复跑结果一致）、可重算、每次判定留日志（why merged/rejected）、**人工可推翻**（"这不是同一件事"→ 拆分并反馈到规则/阈值）。

### 5.4 防自引用（红线）

如果 agent 自己的输出回流后又被当作"外部证据"检索回来，就会出现**回音室**：自我复读 → 看起来多源互证 → 置信度虚高。必须：

- 派生内容 `origin=derived`，检索与 prompt 中显式标注"**内部生成**"（界面来源徽文案）；
- 派生内容**可被引用为证据**，但必须附**根来源索引**——沿推导 DAG 算出的外部源根集合（`doc_id+page` / `series_id@ts`），可逐级点回；根集合为空的额外标"推断"（D-018 §2）；
- 派生断言不计入独立证据数：佐证强度只按不同根来源计数，agent 复述不加分；
- **晋升门**：只有人工确认或独立外部源互证，才能把派生断言升为"已确认断言"（晋升留痕）。

### 5.5 冲突、修订与晋升

- 同槽位异值不覆盖，生成 `conflict`，进入冲突队列；下游可用"暂定"值继续（R3）。
- 修订保留 vintages（与 `architecture.md` §3.4 的时序修订语义一致：修订即新版本）。
- 派生晋升、冲突裁定、合并/拆分决定均留痕，可回看；人工推翻记录进入规则/阈值调优。

### 5.6 检索期去重

检索管线末端执行 MMR/断言聚类（`architecture.md` §4.2）；派生内容标注并降权，不与外部证据混排；同一断言的多个来源以"N 个来源支持"展示，而不是重复列出。

### 5.7 成本分级与 v1 裁剪

- 外部文档：只做 L0–L2（每天数百页，不做全量断言抽取）。
- 人 + agent 产物与交付结论：做 L3–L4（每天量级小）。
- v1 先落 L0–L2 + 派生标记；L3 断言台账在知识库 v1 之后接入（`plan.md` §8）。

## 6. 从介入中学习：分析协议

### 6.1 介入类型 → 学习内容

| 介入 | 学成什么 |
|---|---|
| 事实更正 | 断言修正 + 数据/来源偏好 |
| "来源呢？"类追问 | 判断标准：无源不下结论（可强制） |
| 注入框架/观点 | 分析框架条目 |
| 质疑"为什么/如果…" | 推理链要求、反证习惯 |
| 删减/重写 | 表达与结构偏好 |
| 否决/接受 | 判断阈值 |
| 范围调整 | 关注范围/研究议程 |
| 访谈回答（`interview`，D-024） | 画像、关注点、框架候选（§6.6） |
| 历史产出（冷启动摄取，D-024） | 框架条目、常看指标与图表偏好、表达结构、反复出现的问题（§6.6） |
| 复盘结论（call 裁决后，D-020） | 协议候选 + 来源校准更新（§9）；不自动降级用户显式规则 |

### 6.2 蒸馏流程与门槛

- 触发：定稿后即时（本会话介入）、夜间合并（含未定稿草稿的显式介入、跨日压缩与去矛盾）、用户手动"总结最近习惯"（D-018 §6）。
- 候选规则 `{类型, 陈述, 作用域（品种/阶段/交付物类型）, 证据（介入 id）, 置信度}`。
- 门槛：复发 ≥2 次，或用户显式教导（`pin_rule`）；单次改稿不升级为全局规则；与既有规则冲突交用户裁决。
- 来源登记：规则带 `source ∈ {intervention, pin_rule, bootstrap, postmortem}`，四类分开登记与展示；`bootstrap`（§6.6）与 `postmortem`（§9）不自动 active。

### 6.3 生命周期与透明页

- 状态：`proposed → active → retired`；版本化，可回退。
- 生效方式：注入分析上下文；输出显示"本次应用 N 条规则"可展开。
- **透明页**（"Agent 学到的"）：每条规则可看证据、置信、作用域、来源（§6.2）与**校准**（该规则参与的 call 命中率，§9），可编辑/停用/删除；访谈入口（§6.6）与镜子开关（§9）在此页。
- 显式教导优先：用户说"以后都这样"直接 `pin_rule`，不经复发门槛。

### 6.4 自迭代指标（"越用越懂用户"的可验收定义）

| 指标 | 含义 | 期望方向 |
|---|---|---|
| 交付一次通过率 | 首次交付后未要求重做的作业比例 | ↑ |
| 人改率 | 每份交付物的块编辑数/总块数 | ↓ |
| 返工轮次 | 同一作业的交付重做次数 | ↓ |
| 追问密度 | 每份交付物的"为什么/依据"追问数 | ↓ |
| 交付周期 | 作业从创建到定稿 | ↓ |
| 断言溯源覆盖率 | 可回链来源的断言比例 | ↑ |
| 冲突解决时长 | 冲突从产生到裁定 | ↓ |

**结果指标（L4，D-020）**：以市场结果为锚，定义与裁决规则见 §9。

| 指标 | 含义 | 期望方向 |
|---|---|---|
| agent 校准分 | agent 的 call 的 Brier / 命中率（按品种、类型、时限分桶） | ↑ |
| surprise 捕获率 | 重大数据 surprise 或行情变化前，议程 / 在持观点已覆盖的比例 | ↑ |
| 发布 → 洞察时延 | 数据发布到 surprise 与"依据已变"进议程的时间 | ↓ |
| call 裁决率 / 无法裁决率 | 到期 call 中自动裁决的比例 / `unresolved` 的比例 | ↑ / ↓ |

**护栏**：上表第一组（满意度指标）是约束而非目标——任何以结果指标为目标的协议 / 模型 / 主体变更，若使一次通过率、人改率、返工轮次、追问密度显著恶化（阈值由 feature spec 定），回退该变更。

### 6.5 过拟合防护

- 单次干预不升级为全局规则；时间衰减 + 周期整合。
- 规则可停用/回退；协议变更留痕。
- 用户显式教导与隐式学习分开登记，前者优先。
- 校准不自动降级：agent 不得因校准结果覆盖、停用或降权 `pin_rule` 规则、用户确认的断言与人填槽位（§9 用户优先）。

### 6.6 协议冷启动（D-024）

- **历史产出摄取**：用户指定历史报告 / 笔记 / Excel 模型目录 → 知识层摄取（L0–L2），归类为用户历史分析（派生区，作者 = 人，§5.1）；其中引用的外部数字可抽为断言但须回链原始源，回链不到标"用户转述"、不计独立证据。
- **蒸馏**：蒸馏员读历史产出 → 框架条目、常看指标与图表偏好、表达结构、反复出现的问题 → `proposed` 规则（证据 = 文档定位，`source=bootstrap`）；门槛：复发 ≥2 份文档或透明页显式确认；不自动 active。
- **首启访谈**：首次启动或在透明页重做；结构化问题（每日先看什么、关注品种 / 地区 / 合约、分析框架、什么算证据与禁区、表达偏好）→ 画像 / 关注点 / 协议候选；记为介入事件 `kind=interview`；可跳过。
- 历史产出中的立场**不生成 call**（历史判断的信息环境不可重建，不进校准）。
- 冷启动规则可整体停用 / 回退；§6.5 防护不变。

## 8. 落地边界

### 8.1 非目标（v1）

- 完整自由的块编辑器（v1 只做轻量块模型 + 批注 + 版本/diff/定稿）。
- 外部文档全量断言抽取（成本与噪声不可接受，见 §5.7）。
- 无审核的自动学习（协议候选必须经透明页；显式教导除外）。
- 跨用户共享分析协议（后续商业化评估）。
- 多主体辩论、作业树（§12）；世界模型求解器 / 敏感性 / 情景（§10）；自主度 A3 自扩展（§11）；券商账户 / 成交导入、纸面组合（§9）——均后置，见 `plan.md` §8。

### 8.2 阶段与排序

阶段划分、排序原则与依赖见 `plan.md` §8；指标定义见本文 §6.4。

## 9. 结果校准（L4，D-020）

### 9.1 真值锚与用户优先

- **真值锚 = 市场结果**，在不显著降低用户满意度的前提下（§6.4 护栏）。
- **用户优先**：用户常掌握模型不知道的隐藏或非公开信息，其判断的权限级别在大部分时候高于 agent 与校准信号。agent 不得因校准结果自动覆盖、停用或降权 `pin_rule` 规则、用户确认的断言与人填槽位；校准结果只以信息呈现（§9.5 镜子）。
- **依据类型 `basis`**（§3.4）：`private` 的判断不要求溯源、不被质询来源、不计入来源校准，仍进入决策日志与用户自查校准。

### 9.2 Call

```
call { id, statement, horizon | trigger, resolution_rule(data / event), confidence,
       author(人 | 角色@主体), basis, anchor(block_id / crux_id), status, resolved_at, evidence_asof }
```

- 有可检验含义的结论在**定稿**时由 agent 抽取为 call（定稿效果 ④，§3.5）；crux（§12）可直接登记为 call；用户可自行登记。
- **agent 的 call 不需用户确认即可登记**（作者显式标 agent，是 agent 对自己陈述的负责）；用户可改置信、改裁决标准、丢弃（`decision` 介入）。
- call 是验证性需求的第五类，进验证队列；采集计划类型为"裁决取证"（到期自动取数）。

### 9.3 裁决

- 时限到期或触发满足 → 作业引擎按 `resolution_rule` 取证（数据层序列 / 断言台账 / 事件）判定 `hit / miss / unresolved`；需要语义判断的由值班员（§11）给出建议，交人裁定。
- 裁决留痕（证据 asof、判定理由）；人可推翻（`decision` 介入），推翻记录进入裁决规则调优。
- 裁决触发：一致性台（§11）命中触发条件、日历到期、人工"现在裁决"。

### 9.4 三方校准

| 对象 | 统计 | 用途 |
|---|---|---|
| agent（按角色@主体） | 命中率、Brier；按品种 / 类型 / 时限分桶 | 协议规则置信、"本次应用规则"权重参考、主体排序（§12） |
| 来源（按 source / 机构） | 其断言被 call 裁决验证的命中率 | 检索权重与共识权重的新输入；与 D-017 多源互证计数并列，不替代 |
| 用户 | 自己的 call 与决策的命中率 | **只向用户呈现**；不自动调整用户规则 |

### 9.5 镜子

校准信息的呈现形态，不是动作：立场 vs 市场（在持观点与价格 / 数据走势并置）、跨作业一致性提示（"看多裂解但看空开工"）、被驳回证据的后验命中率。可整体或按作用域关闭（透明页）。

### 9.6 决策日志与自动复盘

- **决策日志**：`decision { statement, direction, anchors(block / call), basis, created_at, postmortem_link }`；agent 从定稿交付物建议起草，人确认登记；v1 手工录入，不接券商账户。
- **自动复盘**：call 裁决后由格物角色生成复盘草稿（当时说 / 结果 / 漏了什么 / 协议候选 / 来源校准更新），进格物致知"复盘"与收件箱（§4.1）；用户可忽略；复盘结论经透明页才成协议（`source=postmortem`，§6.2）。

### 9.7 范围

- Phase 2B：call 登记与自动裁决、决策日志；Phase 2C：自动复盘、校准看板。
- 历史产出中的立场不生成 call（§6.6）；纸面组合、券商导入、跨用户匿名基准为候选（`docs/agent/candidates.md`）。

## 10. 世界模型（D-021）

### 10.1 定义与边界

- 世界模型 = 品种包 schema 定义的市场状态**槽位集合**；一个品种包一个模型；底座品种无关。
- **不是新存储**：槽位值由断言台账与观测投影 / 物化而来；谱系与版本沿用 §5 / D-012；时序观测只在数据层，模型只引用 `series_id@asof`。

### 10.2 槽位

```
slot { key(量 / 地区 / 期 / 口径), value, unit, confidence, sources[], updated_at, staleness,
       value_kind(观测 | 断言 | 估计), status(草稿 | 暂定 | 已确认 | 冲突), author }
```

- 估计 = 求解器 / agent / 人填；**人填的槽位 agent 不得覆盖**（可标冲突）；人填 = 介入事件 `slot_fix`（§3.4），走版本与闸门。
- 陈旧度按槽位类型显示（陈旧徽），衰减策略为候选。

### 10.3 两视图与分歧

- **基本面视图**（供需 / 库存 / 流向 / 开工 / 成本…）与**市场隐含视图**（曲线、价差、持仓…）。
- "基本面 vs 市场隐含"分歧是一等查询（油品 v1 schema 必含）：分歧 → 分析台结论候选 + 验证性需求来源（§3.6）。

### 10.4 一致性与求解

- 品种包声明**恒等式**与允差；**L3.5 模型一致性门**（§5.2）：违反不拒绝 → 标冲突 + 冲突队列 + 验证性需求。门是代码，对账员只解释与建议。
- 求解（后置，Phase 2D）：残差分配、估计填补、**敏感性**（各输入对关键槽位 / 在持观点的影响 → 议程排序输入，§11）、**情景**（"若…则…"传导，用户修枝）。

### 10.5 投影与人的角色

- 平衡表页、图表块、议程中的数字由槽位渲染，带来源徽 / 状态徽 / 陈旧徽；定稿冻结所引用槽位版本（§3.5）。
- 人：填估计、指定口径、裁冲突、标 `basis=private`；agent：维护投影、解释残差、提议估计。

## 11. 常驻研究台与自主度分级（D-022）

### 11.1 常驻作业

```
standing_job { duty, trigger(日历 | 数据写入事件 | 价格/序列阈值 | 文件系统事件 | 定时),
               scope(品种 / 序列 / 作业), output_kind, autonomy_required, budget }
```

- 常驻作业是作业的子类，由作业引擎按触发器调度（编排在代码里，D-019）；产物进收件箱 / 议程 / 平衡表页，不弹窗（R6）。
- 状态见 §3.7；超预算降级为提案。

### 11.2 v1 职责集（"台"，集合由 feature spec 冻结）

| 台 | 触发 | 做什么 | 产物 |
|---|---|---|---|
| 晨间台 | 定时（开盘前） | 装配晨间议程 | 议程 |
| 数据台 | 发布日历 / 数据写入 | 发布前预期表（季节性 / 历史 / 一致预期）→ 发布后 surprise；修订与异常标记 | 议程条目、增量版本触发（§3.6） |
| 一致性台 | 数据写入 / 槽位变化 | 对照在持观点、call、人填槽位；给受影响块打"依据已变"；触发 call 裁决（§9.3） | 议程条目、裁决 |
| 图书馆员 | 文件系统事件 | `docs_in/` / `clips/` 新材料自动摄取；断言陈旧标记；共识地图后置 | 入库记录 |
| 教练 | call 裁决 | 排程复盘（§9.6） | 复盘草稿 |
| 夜间整合 | 定时（夜间） | D-018 §6 夜间合并扩展：协议合并（蒸馏员）+ 断言归并与矛盾、明日预期表预算（值班员） | 协议候选、冲突、预期表 |

### 11.3 晨间议程

- 条目 = 变化 / surprise / 依据已变 / 到期 call / 待裁冲突 / 待介入；排序 = 变化幅度 × 与在持观点和关注的相关度 × 决策临近度（规则由 spec 定；§10.4 敏感性落地后作为输入）；每条下钻到槽位 / 块 / 来源。
- 焦点带承载议程头部；议程不定稿、不回流、过期归档。
- **日报降为导出模板**（§2.4）：仍以提供信息为主，固定模板不变，由议程 + 定时作业交付物生成。

### 11.4 自主度分级

| 档 | agent 可以 | 审批点 |
|---|---|---|
| A0 执行 | 只跑人 / 定时创建的作业 | — |
| A1 提案（建议默认） | 提议作业、计划 DAG、子作业、验证卡、协议候选 | 人确认后执行 |
| A2 常驻 | 常驻作业自动运行并写收件箱 / 议程；自动创建"验证追踪 / 裁决取证"类子作业（只读取数与登记） | 产物进收件箱，可回看；新分析作业仍要确认 |
| A3 自扩展 | 沙箱内编写适配器 / 图表模板 / 处理函数 | 复核员（异模型）审查 + 人批准后注册；网络白名单；Phase 4 |

- 用户可配，可按作用域不同；档位名与默认档以 settings spec 为准。
- **不随档位放松**：破坏性动作确认（R4）、写入闸门（§5）、用户优先（§9.1）、最小权限（D-019）。
- **预算**：每日 / 每台 token 预算，叠加 D-019 每角色 / 每作业上限；超预算降级为 A1；预算与档位在设置与作业详情可见。
- 角色：新增**值班员**（standing job 默认执行角色），见 `architecture.md` §5.5。

## 12. 多主体协作（D-023）

### 12.1 主体

```
persona { id, name, focus_and_framework(协议子集 | 协议包), model_binding(档位 | 物理模型), scope }
```

- 主体是**角色实例化时的视角参数**，与 D-019 角色正交：角色定"做什么"，主体定"以什么视角 / 框架 / 模型做"。内置：基准、多头、空头、红队、用户人格（协议 + 画像生成）；用户可建 / 改。
- 主体产物来源徽 `agent:<角色>@<主体>`；主体互引不计独立证据（§5.4）。

### 12.2 作业树

- 作业可有子作业（按主体或分解维度）；子作业由**作业引擎**创建（人发起或 A1 提案），各跑固定 DAG，产物与介入独立版本化；父作业在分析阶段合成。D-019 编排者的分析阶段内派发是作业树之外的轻量形态。

### 12.3 辩论协议与 crux

1. 冻结证据集（asof）；
2. 各主体的分析员各出最强案例：结论 + 证据链 + 预死亡分析（"若三个月后错了，最可能为什么"）；
3. **裁判员**（strong 档、只读、默认异模型）产出分歧地图 + **crux**（若知道即可裁决的事实、期望来源、裁决标准）+ 共识部分；裁判只引根来源，不引主体结论；
4. crux → 验证性需求 / call（§3.6、§9.2）；用户在分析台裁定、追问任一主体。

### 12.4 用户人格红队

交付前可选一轮（默认关）：用户人格主体按协议生成预期反对意见，撰稿员先回答。红队产物是分析阶段产物（版本化、`origin=derived`），**不是介入事件**。

### 12.5 成本与范围

- 每作业可选（默认关）；消耗 = 主体数 × 分析员 + 裁判员；受每作业上限约束；A2 常驻作业默认不跑辩论。
- 主体是 §9.4 校准的分桶维度；校准不自动停用用户自建主体。
- Phase 2D；协议包导入 / 分享为商业化候选。
