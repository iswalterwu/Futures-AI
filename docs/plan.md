## 1. 背景与目标

期货市场信息极度碎片化，现有工具存在五个痛点：

1. **数据分散**：不同供应商的时间序列难以合并成一张图/表，人肉搬运成本高；
2. **日报死板**：日报由数据供应商撰写，不按用户关注点与用户自己的分析逻辑呈现，缺少交易与基本面指引；
3. **框架不可迭代**：如油品全球平衡表这类"活框架"，在数据源分散、信息碎片化、变化频繁的市场下缺乏持续迭代的实操性，自动化工具无法保证信息可追踪与变化分析；
4. **专题研究低效**：写报告只能手工过一遍手头工具与内容，无自动化工具；
5. **人与自动化割裂**：现有工具把四阶段全部交给机器，人的判断只能事后口头补充、进不了流程；交付完成即结束，不产生下一轮问题；复盘与学习没有承载。

**目标**：做一个本地化的 Agent+人 研究工作台——用户安装后指定文档目录授权读取，程序将外部材料与 agent 产出沉淀为**带溯源的知识底座**；用户自选数据源接入；以作业为单位人机共同交付，人可在任意阶段补充介入但不干扰自动化；交付物生成验证性需求驱动下一轮采集；另设格物致知区支持复盘与认知强化；agent 在作业之外按触发器值班（晨间议程、surprise、一致性报警）。越用越懂用户（分析协议自迭代），越用越准（结果校准，用户判断优先）。

## 2. 产品定位与核心循环

- **定位**：Agent+人 的本地研究工作台——以"作业"为单位人机共同交付，交付物反哺下一轮问题，学习与交付共享带溯源的知识底座（交互与协作模型权威：`interaction.md`）
- **用户**：其他期货交易者（非自用）；下载安装，数据与知识库留在用户本机
- **核心循环（双循环）**：交付循环 = 数据提取 → 数据处理 → 分析延申 → 交付物 →（验证性需求）→ 新作业；学习循环（产品区：格物致知）= 用户发起 → 阅读/复盘/深挖 → 认知产物 → 回流知识底座与分析协议。两循环共享底座，图见 `interaction.md` §2.2
- **执行形态**：作业引擎（Python）推进固定 DAG，各节点由不同角色的 agent 执行（剪藏员 / 对账员 / 分析员 / 撰稿员 / 复核员 / 蒸馏员 / 格物），模型按 fast / standard / strong 三档路由（D-019）；交付物经用户**定稿**（显式动作）后才回流、晋升、派生验证性需求与蒸馏（D-018）
- **主导对象**：作业；对话是接口之一。模块工作台负责"看"（常驻监测），作业负责"做"（交付），**常驻作业**负责"值班"（触发器驱动的研究台：晨间台 / 数据台 / 一致性台 / 图书馆员 / 教练 / 夜间整合，主产物为晨间议程；D-022，`interaction.md` §11）
- **世界模型**：品种包 schema 定义的市场状态槽位集合，是断言台账 + 观测之上的视图；两视图（基本面 / 市场隐含）、恒等式一致性门 L3.5、交付物为其投影；人填槽位 agent 不覆盖（D-021，`interaction.md` §10）
- **自迭代四层**：L1 产物迭代（版本/重跑）、L2 协议迭代（介入→分析协议）、L3 知识迭代（写入闸门+断言台账+验证性需求）、L4 校准迭代（calls 裁决 + 三方校准 + 决策日志 + 自动复盘）；验收指标见 `interaction.md` §6.4
- **真值锚**：市场结果，在不显著降低用户满意度的前提下（满意度指标为护栏）；用户常掌握非公开信息，其判断权限优先，校准只以"镜子"呈现、不覆盖人的判断（D-020，`interaction.md` §9）
- **agent 自主度**：A0 执行 / A1 提案 / A2 常驻 / A3 自扩展，用户可配（建议默认 A1）；闸门、用户优先、破坏性确认不随档位放松（D-022）
- **多主体**：主体（persona）是角色实例化的视角参数；作业树、辩论协议 + 裁判员 + crux、用户人格红队；每作业可选（D-023，`interaction.md` §12）
- **v1 垂直**：油品（柴油/LPG 等能源品种）；底座围绕三大品种无关模块：**供需、物流、期货市场交易数据**
- **模板策略**：v1 图表用固定模板；**日报降为导出模板**（仍以提供信息为主，固定模板不变；晨间议程为常驻作业主产物，D-022）；交付物 v1 为轻量块模型（编辑/批注/版本/diff/定稿），完整自定义编辑器后置
- **协议冷启动**：Phase 1 摄取用户历史产出 + 首启访谈 → proposed 规则，经透明页确认（D-024）

## 4. 文档体系规划

原则：**单一作者、机读优先、决策留痕**（继承 FTEngine 的教训与优点）。

```
docs/
├── plan.md            # 本文档：总方案与路线图（唯一"当前状态"入口）
├── architecture.md    # 产品架构：分层、数据底座、知识层、agent 集成、交付管线、授权
├── interaction.md     # 交互架构：双循环、作业与四阶段契约、介入机制、知识回流、学习与协议
├── designUI.md        # 全局设计理念：配色、图表系统、chart-spec、交付物块模型、组件、界面形态
├── decisions/         # ADR：YYYYMMDD-<slug>.md，编号 D-XXX；先登记再实现
├── data/              # （后续）数据模型、序列规范、适配器 SDK 规范、溯源对齐规格
├── agent/             # candidates.md：agent 工作流候选池（未决想法，含状态与依赖）；（后续）pi 集成细节、工具清单、记忆模块设计、prompt 约定
└── business/          # （后续）收费框架、授权协议、分发与更新、隐私合规
specs/<feature>/       # 功能规格目录：每功能一份 spec/plan/tasks/review（唯一实施入口）
templates/             # spec-driven 工作流模板（spec/plan/tasks/checklist/review 的模板权威）
design/                # FTEngine 移植的规范资产（charts/、ui/，逐份搬运、保留原文编号）
```

文档纪律：

- 每份规范只有一个权威作者位置；README 只导航不复制数值（防双份漂移）
- 交互与协作模型只在 `interaction.md` 维护；`architecture.md` / `designUI.md` 引用不复述（阶段契约、闸门判定、指标定义不重复登记）
- 所有"为什么"写进 ADR 或规范条目，不散落在会话里
- 方案变更先改 docs 再改代码；实现与 docs 冲突以 docs 为准
- **功能开发一律走 spec-driven 工作流**（AGENTS.md §2）：Constitution → Spec → Clarify → Plan → Checklist → Tasks → Analyze → Implement → Converge → Review → Handoff；规格与实施产物在 `specs/<feature>/`

## 6. 架构总览

五层：**Shell（桌面外壳）→ Frontend（Web 前端）→ Backend（Python 核心）→ Storage（DuckDB/LanceDB/SQLite + 用户数据目录）**，
外加两个横向存在：**pi agent 子进程池**（按角色多会话，Backend 经 RPC 驱动，工具经本地 MCP server 暴露，模型三档路由，D-019）与 **license 模块**。
Backend 内新增三块：**作业引擎**（阶段状态机/版本/介入/验证性需求/calls/常驻作业/作业树）、**知识写入闸门与断言台账 + 世界模型**（D-021）、**学习与协议蒸馏 + 校准**（D-020）；"报告管线"升级为"交付管线"，晨间议程是常驻作业的主产物、日报是其导出模板（D-022）。
各层职责、组件与数据流见 `architecture.md`；交互模型见 `interaction.md`。

## 7. 扩展性设计

### 7.1 app 端拓展

- Backend 设计为 headless 核心（localhost API，前后端严格边界），外壳可替换：桌面 v1；后续移动端/远程只读通道（同核心起服务）、CLI 均可低成本接入
- 前端组件与图表渲染不依赖外壳专属 API
- 品种扩展：数据适配器 + 品种配置包（模板/口径/页面）插件化加载，底座不动

### 7.2 模型接口对接

- **agent 主路径**：pi 自带模型体系（内置 providers + `models.json` 自定义兼容端点）。用户自填 API key（DeepSeek/GLM/Qwen/OpenAI/Anthropic 等），设置界面写入 pi 配置；token 成本由用户承担
- **模型三档**（D-019）：用户在设置里为 fast / standard / strong 各指定一个物理模型（只配一个 provider 时可同模型）；角色按档位经 pi 虚拟模型 `futures/auto` 路由；复核员默认异模型；每作业成本上限与成本显示
- **主体模型绑定**（D-023）：主体可绑定档位或指定物理模型（如"多头用 A、空头用 B"），裁判员默认异模型；常驻作业有每日 / 每台预算（D-022）
- **非 agent 用途**（嵌入/精排/解析）：全部本地——bge-m3 + bge-reranker-v2-m3 + MinerU/OCR（见 D-009），隐私与零 token 成本；API 嵌入仅作备选
- **后续**：官方订阅档位含内置模型额度（经我方计费网关），与收费框架联动

### 7.3 数据源接口对接

- **适配器 manifest 规范**（草案，落地时入 docs/data/）：声明可产出序列（描述符）、源符号映射、取数模式（批量/按需/实时）、更新语义（时滞/修订）、凭证要求
- v1 内置适配器：akshare（免费行情/基本面）、EIA（能源公开数据）、本地文件（CSV/Excel 自动识别）
- 第三方适配器：用户安装适配器包 → 程序扫描 manifest → 自动进目录
- 凭证存用户本地目录，绝不外发；软件不转售行情（合规底线）
- agent 数据工具：`search_series` / `fetch_series` / `list_sources` / `reconcile`（完整工具集见 `architecture.md` §5.2）

### 7.4 收费框架

- **模式**：桌面软件 + 激活码（买断或订阅，最终形态待定但架构预留）
- **分层草案**：基础版（内置免费数据源、固定模板图表与日报）/ 专业版（图表与日报自定义、记忆全功能、更多适配器）/ 机构版（多品种、高级对齐与对账）
- **协作与学习能力分层（候选）**：分析协议、验证监测、格物致知、断言台账高级能力（冲突队列/晋升）、多角色与升档、自主度 A2 / A3 与常驻职责数量、多主体辩论、校准看板、世界模型求解 / 情景作为专业版/机构版功能开关，具体分层在商业化阶段确定；协议包导入 / 分享为商业化候选（`docs/agent/candidates.md`）
- **技术**：签名 license 文件（本地）+ 周期在线校验 + 离线宽限期；**feature flags 从第一天贯穿**（功能矩阵随 tier 切换）
- **合规**：用户自带数据源凭证；不代购、不转售行情数据
- **与模型计费联动**：内置模型额度按 tier 计量（后续）

排序原则（为什么不是先做学习、也不是把闸门后置）：

1. **写入闸门 v0 必须与知识库 v1 同期**：agent 一旦开始 `kb_write`，没有闸门就会"先污染后治理"。
2. **格物致知晚于介入数据积累，但协议冷启动不等介入**（D-024）：介入蒸馏仍需数周记录；用户的历史产出与首启访谈在 Phase 1 就能给出 proposed 协议，避免首周"不像用户"。
3. **先"可介入、可迭代、可溯源"，再"自动学习"**：Phase 1.5 只做协作骨架，断言台账与自动蒸馏后置。
4. 各阶段验收对照 `interaction.md` §6.4 的自迭代指标（含结果指标与护栏）。
5. **真值锚后于交付骨架**（D-020）：call 需要可回链的块与验证卡（1.5 / 2B），校准看板需要裁决积累（2C）。
6. **世界模型先投影后求解**（D-021）：先把断言台账投影成槽位并跑一致性门（2A），再做求解 / 情景（2D），避免 schema 未稳就把估计写进模型。
7. **常驻作业复用作业引擎**（D-022）：常驻作业只是带触发器的作业，随调度器（2B）落地，不另起编排。
8. **多主体最后**（D-023）：依赖协议（人格 = 协议子集）、作业树与预算控制。

## 10. 风险与约束

- **数据源合规**：软件不转售行情；适配器只做"用户自带凭证的通道"，来源稳定性风险由适配器层隔离
- **Windows 打包与签名**：代码签名证书成本；自动更新通道需稳定
- **本地模型体积与性能**：MinerU/嵌入/精排随包分发使安装包 GB 级；CPU 解析吞吐有限，批量解析走夜间调度（D-009）
- **pi 版本策略**：随包锁定 pi 版本，升级走正式发布流程
- **激活/换机**：无账号体系，激活码换机流程与防滥用需要产品化设计
- **垂直深度 vs 通用底座**：油品做深的同时保持底座干净，避免品种逻辑渗入底座（用插件边界守护）
- **自引用污染**：派生内容回流后被当作外部证据 → 回音室与置信虚高；对策：D-017 的派生隔离、晋升门与检索标注
- **去重误杀/漏并**：同一事实被错误合并或重复入库；对策：判定留痕（why merged/rejected）、人工可推翻、阈值可测、冲突队列
- **学习过拟合**：单次干预被当成全局偏好；对策：复发门槛、显式教导优先、规则可停用/回退、周期整合
- **介入合并冲突**：旁路编辑与 agent 修改冲突导致流程停滞；对策：冲突不阻塞、定稿检查点集中处理（`interaction.md` §3.3）
- **范围膨胀**：双循环 + 学习显著扩大范围；对策：Phase 1.5 只做"可介入/可迭代/可溯源"，断言台账、自动蒸馏与格物致知后置
- **网页提示注入**：剪藏页面可嵌入指令；对策：剪藏员零工具、输出 schema 与数字守恒校验、抓取仅用户触发（D-018）
- **多角色成本失控**：角色多、升档重跑放大 token 消耗；对策：每角色上限、每作业上限、升档最多一次、成本可见（D-019）
- **校准反噬满意度**：以结果指标优化会让 agent 与用户对抗；对策：满意度指标为护栏、用户优先、镜子可关、`basis=private`（D-020）
- **私有信息判断不可验证**：`basis=private` 可能被滥用为"免溯源"；对策：仍进决策日志与用户自查校准，不进来源校准，透明页可见占比
- **世界模型 schema 僵化 / 估计污染**：schema 定错或求解器把估计写进可信区；对策：schema 在品种包内版本化、先投影后求解、估计值类型显式、一致性门只标不拒（D-021）
- **自主度越权**：常驻作业或自扩展超出用户预期；对策：A0–A3 分档、破坏性确认与闸门不随档放松、A3 沙箱 + 异模型审查 + 人批准、预算降级（D-022）
- **常驻与多主体成本**：值班与辩论持续消耗 token；对策：每日 / 每台预算、辩论默认关、常驻作业不跑辩论、成本在议程与作业详情可见（D-022 / D-023）
- **冷启动规则偏旧**：历史产出反映的是过去的框架；对策：`source=bootstrap` 分开登记、不自动 active、可整体停用、历史立场不进校准（D-024）
