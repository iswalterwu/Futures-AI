# D-019 多 agent 编排：角色、固定 DAG、模型三档与最小权限

- 日期：2026-10-28
- 状态：accepted
- 关系：补充 D-003（pi 经 RPC 驱动、工具经 MCP）与 D-016 结论 2（作业引擎编排）；不改变 D-012 单写者与进程内 MCP
- 相关：`architecture.md` §5（新 §5.5）、`plan.md` §7.2/§8、`designUI.md` §3.6、`interaction.md` §3.2、D-018

## 背景

作业的四阶段任务难度差异很大：网页清理排版是机械变换，断言与证据链生成是重推理，复核需要独立视角，蒸馏需要读长台账。单一模型、单一会话跑完整条流水线既浪费（简单任务用强模型）又不稳（强推理任务被上下文稀释、无人复核）。Walter 2026-10-28 裁定：采用多 agent 编排。

## 备选方案

- **A（采纳）**：角色化 + 固定 DAG：角色 = 定义文件（系统提示 + 工具子集 + 模型档），作业引擎（Python）按阶段调用；模型三档由 pi 虚拟模型路由；复核员独立；v1 不设编排者 agent
- B 单 agent 单会话：实现最简，但难度无法分层、无独立复核
- C agent 自由编排（编排者 agent 动态拆任务并推进阶段）：灵活，但阶段 / 版本 / 介入无稳定宿主，违反 D-016"作业引擎编排、pi 不推进阶段"

## 结论

1. **原则：编排在代码里，智能在节点里。** 作业引擎（`backend/workflow/`）是固定 DAG 的唯一推进者；每个节点由一个角色执行；pi 不推进阶段、不直接改产物最新版本（D-016 不变）。
2. **角色**（定义文件沿用 pi `agents/*.md` 的 frontmatter：name / description / tools / model + 系统提示；Backend 据此拉起 RPC 会话）：

| 角色 | 阶段 | 任务 | 模型档 | 工具子集 |
|---|---|---|---|---|
| 剪藏员 | 提取 | 网页清理排版、来源说明建议、别名建议 | fast | **无**（纯变换） |
| 对账员 | 处理 | 单位 / 日历 / 口径核查、对账摘要、派生序列建议 | standard | data 只读 + `reconcile` |
| 分析员 | 分析 | 结论、证据链、chart-spec | strong | kb / data / report 读 + `kb_write` |
| 撰稿员 | 交付 | 按分析协议装配块、执行块级改稿 | standard（改稿升 strong） | `artifact_write` |
| 复核员 | 交付前 | 证据可达、数字一致、来源徽 / 根来源齐全、协议遵循 | 默认与分析员**不同**模型 | kb / data 只读 |
| 蒸馏员 | 定稿后 / 夜间 | 介入事件 → 分析协议候选 | standard | `intervention_read` + `playbook_propose` |
| 格物 | 格物致知 | 复盘 / 阅读 / 深挖 / 笔记 | strong | 只读 + `study_note` |
| 编排者 | 专题（Phase 2） | 在分析阶段内拆子任务、派发、合并 | strong | `dispatch_task` + 全部读 |

3. **模型三档**：`fast / standard / strong`。用 pi 原生虚拟模型注册 `futures/auto`，档位作为路由输入；用户在设置里为每档指定物理模型（自带 key，plan §7.2）；角色文件写 `model: futures/auto:<档>`。用户只配一个 provider 时三档可同模型。
4. **复核员异模型**：用户配置 ≥2 个 provider 时复核员默认用与分析员不同的模型（减少相关错误）；否则同模型不同提示。
5. **升档规则**：复核员打回或节点自报低置信 → 同任务升一档重跑，**最多一次**；仍不过 → 产物标暂定、进待人工确认（不阻塞下游，D-016 R3）。
6. **编排者 agent**：v1 **不设**；Phase 2 引入，且只能在分析阶段内派发子任务（`dispatch_task(role, task, budget)` 由 Backend 兑现：复用 / 新开会话），不能推进阶段、不能越过闸门。
7. **预算与可见**：每角色 token 上限、每作业成本上限；RPC usage 事件汇总成本，作业详情与 CoT 时间线显示角色芯片与成本。
8. **隔离**：最小权限工具子集；写断言 / 产物只经 `kb_write` / `artifact_write`（闸门与版本不变）；剪藏员零工具（提示注入防线，D-018）；DuckDB 单写者不变（所有写经 Backend 进程内 MCP）。
9. **实现形态**：Backend `agent/` 维护按角色的 RPC 会话池（`pi --mode rpc`，每会话独立上下文）；pi 自带 subagent 扩展作参考实现，但控制权留在 Python（D-003 路线）。pi 锁定版本须 ≥ 1.4（虚拟模型 API）。
10. **与开发工作流的区分**：本 ADR 是**产品运行时**的角色与模型档；本仓库开发工作流的模型路由在 `AGENTS.md` §6，两者无关。

## 取舍理由

- 固定 DAG 而非自由编排：阶段 / 版本 / 介入需要稳定宿主，可测试、可恢复；开放式专题的灵活性以"分析阶段内派发"有界地满足。
- 三档而非按模型名硬编码：用户自带 key、模型更迭快；档位是稳定抽象，虚拟模型是 pi 原生机制，不自写路由。
- 复核员独立：同模型自查的相关错误高；异模型复核是最便宜的质量杠杆。
- 升档最多一次：防止成本失控与无限重跑。
- 零工具剪藏员：网页是不可信输入，零工具使任何注入都无法触发动作。
